> A real client's JWT is signed by GoTrue and cannot be forged without the secret, and the

> `auth.uid()` in the harness models the *strongest* real attacker, not a stronger-than-real one.

## 🔴 CONFIRMED EXPLOITS

### F-1 — `complete_delivery` has no caller authorization → delivery-completion forgery + unauthorized payout — **HIGH**
- **Attack path:** authenticated customer → `POST /rest/v1/rpc/complete_delivery` `{p_order_id: <own order>, p_driver_id: <the order's assigned driver>}`. The driver id is readable from the customer's **own** order row (orders SELECT policy `customer_id = auth.uid()`), and `complete_delivery` is `EXECUTE`-granted to `authenticated`.
- **Root cause:** the function verifies only that `orders.driver_id = p_driver_id`. It does **not** verify `auth.uid()` is that driver (or ops). Any party who can see an `on_the_way` order can complete it.
- **Proof (read-back, attacker = the customer, NOT the driver):**
  - `order.status` → **`delivered`** (forced, before real delivery)
  - `driver_earnings` rows for the order → **1** (created)
  - driver wallet balance → **`25.00`** (order's `delivery_fee` paid out)
- **Impact:** a customer can forge completion of their own in-progress order and trigger the platform's driver-payout liability before the goods are delivered — a COD-integrity / dispute-fraud / premature-settlement defect. It is broken function-level authorization (OWASP API1/API5 class). Not double-spendable (idempotent — see BLOCKED list), but a single unauthorized state+money move is sufficient.
- **Remediation (not applied — read-only sprint):** add `if p_driver_id <> auth.uid() and not is_ops_admin() then raise` (mirror `finalize_driver_delivery`'s own guard), or drive completion only from an ownership-checked driver RPC.

### F-2 — `finalize_driver_delivery` lets a driver mutate own dispatch state → concurrency-limit bypass — **MEDIUM**
- **Attack path:** authenticated driver → `rpc('finalize_driver_delivery', {p_order_id: <any>, p_driver_id: self})`. Guard only checks `p_driver_id = auth.uid()`.
- **Root cause:** the RPC (SECURITY DEFINER, runs as owner) writes `drivers.active_orders` and `drivers.status` — the very columns `drivers_guard` (Hardening Pass #3) locks against direct client writes. It is an authorized *bypass* of that lock, with no tie to a real delivered order.
- **Proof (read-back):** `active_orders` **2 → 0**, `status` **`busy` → `available`**.
- **Impact:** a busy driver can reset their workload counter and flip to `available`, defeating `max_concurrent_orders` and biasing `find_nearest_drivers` — the same dispatch-integrity class as RT-1/RT-2, reachable through an RPC the guard cannot see. No direct theft.
- **Remediation:** bind the decrement to a real `delivered` order assigned to the caller (verify the order's status/driver), rather than trusting an arbitrary `p_order_id`.

### F-3 — Merchant confidential/KYC data exposure via always-true discovery policy — **MEDIUM**
- **Attack path:** any authenticated user → `GET /rest/v1/merchants?select=business_name,tax_number,commercial_registration_number,contact_email,contact_phone,owner_user_id,address`.
- **Root cause:** policy `merchants_discovery_read` = `SELECT` to `authenticated` with `USING (true)`, and `authenticated` holds a table-wide column grant → the **entire** merchants row is returned, not just public storefront fields.
- **Proof (read-back):** attacker (an ordinary customer) read a victim merchant's `tax_number = 'TAX-SECRET-9'` (count = 1). Anon is **not** affected (no grant to `anon`).
- **Impact:** every registered user (incl. competitors) can harvest all merchants' tax IDs, commercial-registration numbers, contact details, and owner user IDs — a confidential-business-data / PII exposure.
- **Remediation:** restrict the discovery policy to a public view/column subset (name, logo, cover, location), or move KYC columns to a separate ops-only table.

## 🟡 LOW-SEVERITY WEAKNESSES (not full exploits, but pre-launch hardening)

- **F-4 — Unauthenticated maintenance-function execution.** `anon` can execute `expire_dispatch_offers()` and `recalc_driver_performance(<any driver>)` (no internal guard). **Proof:** both returned successfully under `SET ROLE anon`. Values are recomputed from real data (no injection), but it is unauthenticated compute (DoS surface) + unauthorized writes to `drivers.priority_score` / `driver_performance`. Also `auto_dispatch_order` (anon path) and `cron_dispatch_sweep` (authenticated) are reachable but their effective dispatch work is gated by inner `auth.uid()`/`is_ops_admin` checks.
- **F-5 — Always-true INSERT policies (advisor `rls_policy_always_true`, 3):** `order_status_history` (`Authenticated users can insert order status`), `campaign_events`, `search_analytics`. A client can forge order-history/analytics rows (log-integrity spoofing; `orders.status` itself remains guarded).
- **F-6 — Listable public storage buckets (advisor `public_bucket_allows_listing`, 6):** `avatars`, `banners`, `experience-assets`, `merchant-logos`, `offer-images`, `product-images` allow object **listing** (filename enumeration). `kyc-documents` is correctly **private**.
- **F-7 — Mutable function `search_path` (advisor, 13):** `find_nearest_drivers`, `driver_wallet_summary`, `zone_*`, `resolve_commission_rule`, `haversine_km`, etc. Hardening; pin `SET search_path`.
- **F-8 — `pg_trgm` extension installed in `public` (advisor).** Move to a dedicated schema.

## FINAL DECISION: 🔴 **FAIL**

Three reproducible exploits survived a fresh external attack — one **High** (`complete_delivery`
authorization bypass moving money and forging order state) and two **Medium** (driver
dispatch-state bypass; merchant KYC data exposure). Any one is disqualifying for launch.

**Important context for stakeholders — the remediation surface is small and the prior work is solid:**
- **Every previously-remediated exploit held** under independent re-attack: B1–B8, RT-1, RT-2,
  wallet integrity, privilege escalation, and cross-customer/merchant/tenant isolation. The
  hardening passes were real and effective.
- The three failures are **newly-surfaced authorization gaps**, not regressions, and none is a
  direct-theft-by-attacker or a mass-data breach. F-1 is the only High and is a single missing
  `auth.uid()` check.
- Fixing F-1 (one guard clause), F-2 (bind to a real delivered order), and F-3 (scope the
  merchant discovery policy) — plus the Low items F-4…F-8 — is an estimated **~1 day** hardening
  pass, after which this battery should be re-run.
